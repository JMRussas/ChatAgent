ChatAgent Class Map

The application layer still depends on interfaces, never on a vendor, but the 2026-09-25 picture of three classes and six ports is out of date. The runtime now has two orchestrators selected at startup, a generation lifecycle registry, a context manager with background summarization, an optional catalog dispatch path with discovery and admission, a CLI bridge to Claude, an optional Python sidecar, and a sports evidence subsystem exposed to the model as capability tools. Each diagram below is Mermaid source, so it can be edited as text and diffed. Line and file references were verified against the code on the date above.

1. Composition root — src/server.ts startServer(port)

One function constructs everything. Three environment decisions change the object graph: routing mode (MODEL_ROUTING_MODE=fixed|catalog), whether both providers are mock, and which optional sidecars are configured.

2. Application layer — src/app/

ChatService is the facade the HTTP layer talks to. It owns conversation scoping and ownership claims and tracks in-flight work for shutdown. The two orchestrators share one structural type (handleUserMessage, cancel) and one GenerationLifecycle registry, looked up per TaskQueue instance.

3. Generation attempt lifecycle — src/app/generationLifecycle.ts

Every fast or deep phase of a turn is one GenerationAttempt. A retry creates a new attempt with a new attemptId; the old one finishes with error and retrying = true. Terminal state is claimed synchronously before any await, so cancellation and completion cannot both win.

4. Model and storage ports — src/providers/interfaces.ts, src/app/*Store.ts

The left side is what the application layer holds; the right side is what the composition root constructs. Every live adapter now streams through one shared transport kernel (src/providers/streaming.ts): a single deadline covering headers and body, user abort distinguished from timeout, frame and answer byte caps.

5. Catalog dispatch, discovery and the CLI bridge — src/routing/, src/models/, src/providers/cli/

Present only in MODEL_ROUTING_MODE=catalog. The catalog is curated data; the inventory is fresh observation; readiness is derived from observation and never from configuration. Selection ranks bindings by task requirements, retained context fit and policy.

6. Sports evidence and capability tools — src/sports/

Live chat does not search the web. CapabilityChat asks the model for a plan over the tools BriefingHttp exposes; each tool reads a bounded, attributed SourceResult with explicit coverage and freshness. The shared SportsRequestBudget admits five BALLDONTLIE starts per rolling minute process-wide.

7. Python documentation sidecar — experiments/doc-agent/

Optional, enabled by DOC_TASK_PYTHON. Node and Python exchange one JSON object per line over stdin and stdout; no user text ever reaches a shell. The graph itself is documented in experiments/doc-agent/LANGGRAPH.md, whose flowchart matches graph_agent.py:181-189.

8. Domain data — src/domain/

Attributes only, no behavior. Fields marked optional are absent on the mock-only path.
