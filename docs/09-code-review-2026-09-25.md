## 1. Bugs (most important first)

| # | Status | Finding | Location |
|---|---|---|---|

| B2 | Confirmed | Other cue lists are substring matches. "help me research dogs" routes `deep` because "research" contains "search". | `src/routing/classifier.ts:13`, `src/domain/router.ts:3` |
| B3 | Open | External-data branch replaces a base `clarify` decision with `deep`, while the complexity branch two lines later deliberately preserves `clarify`. The two branches disagree on precedence. | `src/routing/adaptiveRouting.ts:52-57` |
| B4 | Confirmed | `POST /messages` with body `null` returns 500 (`Cannot read properties of null`). Strings and arrays return 400 by accident. | `src/server.ts:113` |
| B5 | Open | Azure and Ollama providers use bare `fetch` with no timeout. A hung fast provider blocks the fast path indefinitely and then records a huge latency sample. | `src/providers/azureProviders.ts:23`, `src/providers/ollamaProviders.ts:9` |
| B6 | Open | Task IDs are `task_<conversationId>_<Date.now()>`. Two messages in the same conversation in the same millisecond collide. Retry counting and dead-letter removal key on this ID. | `src/app/orchestrator.ts:13` |

| B8 | Open | Concurrent saves share one temp path (`<file>.tmp`). An overlapping interval save and close save can race on `rename`, and the rejection is discarded via `void`. | `src/telemetry/latencyTelemetryStore.ts:84`, `src/server.ts:233` |

| B10 | Open | `/routing/policy/tune` trusts a client-supplied `queueDepth` even though the server owns the queue and `InMemoryTaskQueue.size()` exists. | `src/app/chatService.ts:63`, `src/server.ts:158` |
| B11 | Open | `PORT` is passed through `Number()` unvalidated; `parsePositiveIntEnv` already exists for this. | `src/index.ts:4` |

## 2. Design gaps

| # | Finding | Location |
|---|---|---|
| D1 | The deep path is not autonomous. Nothing drains the queue unless a client POSTs `/workers/deep/run-once`. The live benchmark works around this by calling it manually. A worker loop on an interval would make the "async" claim true. | `src/server.ts` |
| D2 | The deep task is enqueued after the fast provider returns, so fast and deep work run in series rather than in parallel. For a perceived-latency prototype, enqueue before awaiting the fast reply. | `src/app/orchestrator.ts:45-68` |
| D3 | Benchmark and eval numbers are synthetic. Simulate mode derives latency and quality from a hash of the profile name. Live mode reports a constant quality per route. Committed reports are all simulate mode; `data/eval-records.json` is hand-authored. This should be labeled clearly in README and report headers. | `src/bench/benchmarkCore.ts:98-110`, `src/bench/liveBenchmark.ts:48`, `reports/` |
| D4 | `benchmarkCore.routePrompt` reimplements routing without the base analyzer or the p95 guardrail, so simulated route rates can drift from what the server does. | `src/bench/benchmarkCore.ts:78` |
| D5 | Dead polling loop: events are re-read four times with no worker run or delay between reads. | `src/bench/liveBenchmark.ts:99-114` |
| D6 | Inconsistent input validation. Telemetry snapshots and prompt files go through zod; benchmark summaries and eval records are cast from raw `JSON.parse`. | `src/bench/compareBenchmarks.ts:6`, `src/eval/generateReport.ts:10` |
| D7 | A non-mock provider with no model silently becomes `"unset-model"` and only fails on the first API call. Should fail at startup. | `src/config/providerConfig.ts:47` |
| D8 | `deepCitationRate` returns 1 when there are zero deep records, so the citation gate passes vacuously on empty data. | `src/eval/metrics.ts:36` |
| D9 | Default policy `{ maxFastP95Ms: 1000 }` is duplicated in three places in `ChatService`. | `src/app/chatService.ts:48,61,84` |
| D10 | No request body size limit or auth on the HTTP server. Acceptable for a local prototype; note it in docs. | `src/server.ts:87` |

## 3. Tests

- Coverage is broad and the integration tests exercise real HTTP round trips, which is good.
- Classifier and router tests cover only happy paths. There are no negative cases guarding against false positives, which is why B1 and B2 survived.
- No test covers a fast provider that never returns (B5).
- Suggested first step: add failing tests for "write a haiku" (expect `low` ambiguity, `direct` route) and "help me research dogs" (expect `externalDataNeeded === false`), then fix B1/B2 with word-boundary matching.

---

## 4. What is solid

- Clean layering: domain, providers, routing, telemetry, and app are separated behind interfaces; the HTTP layer is thin.
- Atomic write plus zod validation on the telemetry store is the right pattern.
- Dead-letter store with replay, and retry accounting in the worker, are sensible for a prototype.
- The engineering decision log is a good habit and already reflects several fixes.

---
