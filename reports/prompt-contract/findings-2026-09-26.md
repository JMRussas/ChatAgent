# Minimum prompt contract — live findings, 2026-09-26

## Result

Completed **600 scored local Ollama calls** across five distinct model digests, 24 cases and five prompt conditions, plus five excluded warmups. Every call finished normally; no transport errors or output truncations. Scoring, cases, renderings and code hashes were frozen before the first inference.

On the 12 new held-out cases, TGR headings produced 40/60 correct responses versus 38/60 for identical content without headings: **66.7% versus 63.3%**, a 3.3 percentage-point difference. Paired outcomes were four wins, two losses and 54 ties. This is a small descriptive difference, not a statistically established improvement.

The old baseline scored 36/60 (60.0%), but it uses different instructions and message placement. That comparison cannot isolate the effect of headings. On the 12 calibration cases, flat scored 52/60 and TGR 51/60; combined they scored 90/120 and 91/120 respectively. The combined difference is only one answer.

## Held-out aggregate and token tradeoff

| Variant | Content accuracy | Strict exact success | Mean input tokens |
|---|---:|---:|---:|
| legacy | 36/60 (60.0%) | 19/60 | 162.2 |
| flat | 38/60 (63.3%) | 29/60 | 242.9 |
| tgr | 40/60 (66.7%) | 31/60 | 254.3 |
| json | 32/60 (53.3%) | 30/60 | 259.9 |
| xml | 35/60 (58.3%) | 35/60 | 302.6 |

TGR used about 4.7% more input tokens than flat text (254.3 versus 242.9), and about 56.8% more than the old baseline. JSON and XML also increased input length. This experiment tests organization while preserving full wording; it does not demonstrate compression. Counts include common instructions and model templates, and cross-model averages mix tokenizers.

Strict output-contract success tells a different story from content correctness: XML had 35/60 exact successes versus TGR 31/60, despite fewer correct selections after presentation normalization. Models that fence answers are especially affected. A production API may value exact output compliance; do not silently substitute one endpoint for the other.

## Model-specific observations

- Qwen3:8b: TGR gained two held-out cases over flat, with no losses.
- Qwen3.5: TGR lost one case against flat; the old baseline and flat tied.
- Gemma4: TGR and flat tied in total with one win and one loss; XML was its highest content score at 11/12.
- Qwen3-coder: TGR gained one case over flat, with no losses.
- Qwen2.5-coder: TGR and flat tied on every held-out case. Its fenced answers prevented exact success for those conditions; XML returned strict answers in the held-out run.

## Design decision supported by this run

Keep **Task / Guidelines / Response Framework** as a clear experimental package boundary, with separately referenced context. Keep readable TGR as a candidate rendering and preserve a flat/prose control. The organizational contract is useful for explicit responsibilities and telemetry even though this experiment does not establish a universal accuracy benefit.

Do not automatically select XML for every model, discard prose, or add a semantic-compression step. Renderer choice should remain configurable. A next application increment can port the interface to TypeScript and integrate one provider behind existing behavior tests. No application renderer, LangChain dependency or provider migration was implemented here.

## Limitations

- One deterministic pass per cell; twelve held-out cases are too few for a reliable general ranking. They are newly authored related synthetic cases, not an independent external benchmark.
- All conditions request JSON output; input/output format affinity is not independently controlled.
- New contract versus legacy also changes instruction wording and placement; TGR versus flat is the narrower comparison.
- Thinking was disabled only where installed metadata explicitly supported it. This is a non-thinking, short-answer task study, not optimal per-model tuning.
- Models run sequentially in fixed order; cases are seeded and format order rotates. Cache, hardware state and remaining model defaults are uncontrolled. Wall latency includes the Windows bridge. No cross-run speed claim is made.
- Sources are short and supplied directly. No live retrieval, long-context assembly, tool calls or real development tasks were tested.
- No LLM judge, tuning after results, output repair, network retry or automatic learned policy was used.
